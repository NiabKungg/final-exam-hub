เคส CS-Hospital (โจทย์จริง — จำไว้ใช้เป็นแม่แบบ)

โรงพยาบาลขนาดเล็ก เปิดให้นักศึกษา/บุคลากรในสถาบัน และรับผู้ป่วยนอกทั่วไป แต่ไม่มีระบบจัดการผู้ป่วย อยากได้เว็บแอปจัดการผู้ป่วย โดย:

  • เก็บข้อมูลผู้ป่วย: ประวัติการรักษา, ผลการรักษา, ผลห้องปฏิบัติการ

1 · จับคู่: Software Testing (7 ระดับ + แนวคิดเสริม)

ภาพรวมลำดับ (ท่องเป็นท่องเดียวจบ) Unit → Integration → (Function → Quality) → System → Acceptance → Installation
เปรียบเทียบเปิดร้านอาหารใหม่: ลองทำแต่ละเมนูที่อาหาร (unit) → ลองจับคู่เมนู+ข้าว+น้ำจิ้มเข้าด้วยกัน (integration) → ลองเมนูตามสูตรครบทุกจาน (function) → ทดสอบคุณภาพรส/ความเร็วเสิร์ฟ (quality) → เลี้ยงลองเมนูทั้งร้าน (system) → ให้ลูกค้าจริงมาชิมแล้วตัดสิน (acceptance) → เปิดขายจริงหน้าร้าน (installation)
ชนิดคำอธิบาย (คำที่จะออกในข้อจับคู่)ใครทำ / เทียบกับอะไร
Unit Testทดสอบโมดูล/คอมโพเนนต์เดี่ยว ๆ แยกจากกัน (in isolation) ว่าถูกตาม unit specificationนักพัฒนา · White-box ส่วนใหญ่ (JUnit)
Integration Testรวมโมดูลที่ผ่าน unit แล้วมาต่อกัน เช็กว่า "คุยกันถูก" (interface ระหว่างโมดูล)Top-down / Bottom-up / Sandwich
Function Testตรวจว่าระบบทำตาม Functional Requirements ครบไหมเทียบกับ FR
Quality Testตรวจ Non-Functional Requirements: ประสิทธิภาพ ความปลอดภัย ฯลฯเทียบกับ NFR
System Testทดสอบระบบสมบูรณ์ทุกส่วนเชื่อมกันแล้ว ตาม system specificationทีมทดสอบ
Acceptance Testลูกค้าทดสอบเพื่อตัดสินรับงาน ด้วยเกณฑ์ความสำเร็จของโครงการ — ส่วนใหญ่เป็น black-boxลูกค้า / ผู้ใช้
Installation Testทดสอบติดตั้ง+ใช้งานจริงในสภาพแวดล้อมของผู้ใช้ (system in use / platform จริง)สุดท้ายก่อนส่งมอบ

White-box vs Black-box

White-box = ทดสอบโดยดู "โครงสร้างภายในโค้ด" (ผู้พัฒนาทำ) — ครอบคลุม statement/edge/condition/path
Black-box = ทดสอบ "ช่องว่างของ input ตาม spec" โดยไม่สนโค้ด (มุมมองลูกค้า) — equivalence/boundary

โจทย์ Midterm เคยถาม: "สามารถแก้ไขซอฟต์แวร์ได้แบบ static ______" → Verification (ตรวจก่อนรันจริง) ต่างจาก Validation (ทดสอบกับของจริง/ผู้ใช้)

เทคนิคหา test case

  • Equivalence testing: แบ่ง input เป็นกลุ่มที่ "ระบบน่าจะทำงานเหมือนกัน" แล้วเลือกตัวแทน (เช่น อายุ 0–100 → valid, <0 และ >100 invalid)
  • Boundary testing: ทดสอบ "ขอบ" — 0, min/max, ช่องว่าง, null, สลับ > กับ ≥
  • Control-flow testing: statement / edge / condition / path coverage
  • State-based testing: ออกแบบจาก state diagram (เช่น ประตู: Locked→Accepting→Unlocked/Blocked) ให้ครบทุก state และ transition
แนวคิด integration / unit เสริมความหมาย (สำหรับจับคู่)
Big-bang integrationรวมทุกอย่างพร้อมกันครั้งเดียว — พังแล้วหาต้นตอยาก
Bottom-upทดสอบจากโมดูลล่างขึ้นบน ใช้ test driver จำลองตัวเรียก
Top-downจากบนลงล่าง ใช้ test stub จำลองตัวถูกเรียก — ผู้ใช้เห็นฟังก์ชันเร็ว
Sandwichผสมทั้งบนและล่างพบกันตรงกลาง
Vertical integrationซอยระบบตาม use case (user story) แล้ว integrate ในแต่ละ slice
TDD (Test-Driven Development)"ไม่สร้าง artifact ไหนถ้ายังไม่รู้จะทดสอบมันยังไง" — เขียน test ก่อน → ให้ fail → เขียนโค้ดให้ผ่าน → refactor
Mock objects / Driver / Stubdriver = จำลอง "ตัวที่เรียกเรา", stub = จำลอง "ตัวที่เราเรียก" — ใช้เพราะของจริงยังไม่มี/ง่ายต่อการหา fault

2 · จับคู่: Software Maintenance (4 ประเภท + ข้อเท็จจริง)

นิยามMaintenance = กระบวนการแก้ไขระบบซอฟต์แวร์หลังส่งมอบ (after delivery) เพื่อแก้ fault, เพิ่มประสิทธิภาพ, หรือปรับตัวกับสภาพแวดล้อมใหม่ · เหมือนบำรุงรักษารถ: ซ่อมเมื่อพัง (corrective), ปรับใช้น้ำมันชนิดใหม่ (adaptive), ติดตั้งอุปกรณ์เสริมตามที่ลูกค้าขอ (perfective), เช็กสภาพป้องกันล่วงหน้า (preventive)
ประเภทเปลี่ยนเพราะอะไรตัวอย่างสัดส่วนจริง
Correctiveแก้ข้อผิดพลาด/บั๊กที่พบหลังส่งมอบโค้ดคำนวณราคาผิดเงื่อนไขหนึ่ง · ระบบ crash เมื่อ user แน่น~21%
Adaptiveปรับให้ทันสภาพแวดล้อมเปลี่ยน (HW/OS/DB)รองรับ OS ใหม่ · เปลี่ยน database เป็นตัวใหม่~25%
Perfectiveตามความต้องการผู้ใช้ที่เปลี่ยน / ปรับปรุงคุณภาพเพิ่มฟังก์ชันจ่าย QR · ปรับ UI ให้ง่ายขึ้น · เร็วขึ้น~50% (เยอะสุด!)
Preventiveเพิ่มความสามารถบำรุงรักษา (maintainability) ป้องกันอนาคตRefactor โครงสร้างโค้ด · เขียนเอกสารเพิ่ม~4%

สิ่งที่ชอบออกเป็นข้อถูก/จับคู่

  • ปัญหา maintenance หลัก: unstructured code, ความรู้ domain ไม่พอ, เอกสารไม่พอ
  • Development vs Maintenance: พัฒนา = อิสระ, บำรุง = ถูกผูกกับระบบเดิม + defect กระทบ production ทันที
  • ช่วงชีวิต: เริ่มต้นเน้น user support → Growth เน้นแก้ fault → Maturity เน้นเพิ่มฟังก์ชัน → Decline เน้นตามเทคโนโลยี
  • ต้นทุน: maintenance แพงกว่า development ตลอดอายุระบบ (กราฟ hardware/software cost)
  • ต้นทุน maintenance ขึ้นกับ: ความเสถียรของทีม, สัญญารับผิดชอบ, ทักษะคน, อายุ/โครงสร้างโปรแกรม

รับคำขอเปลี่ยนแปลง (bug/ปรับปรุง)

Impact Analysis

ประเมินผลกระทบก่อนแก้ (แตะอะไรบ้าง)

Release Planning

จัดคิวจะออกเวอร์ชันไหน

Implementation → System Release

3 · เขียนตอบ: "จะทดสอบระบบและวางแผน Maintenance อย่างไร" (เทมเพลต + ตัวอย่างเต็ม)

โจทย์ข้อนี้จะเขียนว่า"จากโปรเจกต์ที่นักศึกษาทำ นักศึกษาจะ ทดสอบระบบ และ วางแผน Maintenance อย่างไร" — เขียนตอบด้วยโครง 2 ส่วนด้านล่าง แล้วผูกเข้ากับฟีเจอร์ของเคส (CS-Hospital/CS-Pizza) ให้เห็นว่า "ใช้จริง" ไม่ใช่ท่องทฤษฎี

ส่วนที่ 1: แผนทดสอบ (ทำตามลำดับ 7 ระดับ)

① Unit test ทุกโมดูล (เช่น ฟังก์ชันค้นประวัติผู้ป่วย, คำนวณค่ารักษา) ด้วย JUnit + mock DB · ② Integration แบบ bottom-up เชื่อมโมดูลทีละคู่ · ③ Function test ตรวจ FR ทุกข้อ · ④ Quality test โหลด 1,000 user พร้อมกัน, ทดสอบสิทธิ์เข้าถึง · ⑤ System test เฟลว์ครบวงจร · ⑥ Acceptance test ให้แพทย์/พยาบาลใช้จริงด้วยเกณฑ์ที่ตกลง · ⑦ Installation test บนเซิร์ฟเวอร์โรงพยาบาลจริง

ยกตัวอย่าง test case ให้เห็นภาพ: "ส่งผลวินิจฉัยไปทีมเฉพาะทางผ่าน LINE — ทดสอบกรณีไฟล์แนบใหญ่ / อินเทอร์เน็ตหลุด / สิทธิ์ไม่พอ" (boundary + state-based)

ส่วนที่ 2: แผน Maintenance (ครบ 4 ประเภท + กระบวนการ)

Corrective: ตั้งช่องทางแจ้งปัญหา + SLA แก้ critical ภายใน 24 ชม. · Adaptive: ติดตามอัปเดต OS/browser/DB แล้วปรับระบบทุก 6 เดือน · Perfective: เก็บ feature request จากแพทย์-พยาบาล ปล่อยเวอร์ชันใหม่ทุกไตรมาส (เช่น เพิ่มสถิติผู้ป่วย) · Preventive: code review + refactor รายไตรมาส, อัปเดตเอกสาร, สำรองข้อมูลทุกวัน

ปิดท้ายด้วย "กระบวนการ"

Change Request → Impact Analysis → Release Planning → Implementation → System Release — พร้อมย้ำว่า "ทุกการแก้ต้องผ่านการทดสอบซ้ำ (regression) ก่อนปล่อย"

4 · Functional & Non-Functional Requirement ⭐ (ออกเกือบทุกปี)

สูตรแยกให้ได้ใน 3 วินาที FR = ระบบ "ต้องทำอะไร" (What the system will do) — ฟังก์ชัน พฤติกรรม การตอบสนอง input
NFR = ระบบ "ทำได้ดีแค่ไหน" (How well it does it) — คุณภาพ ข้อจำกัด มักอ้างกรอบ FURPS+
FURPS+หมายถึงตัวอย่างเขียนในข้อสอบ
Functionality (Security)ครบฟังก์ชัน + ปลอดภัยป้องกัน Dictionary Attack: รหัสผิดเกิน 3 ครั้งล็อกบัญชี
Usabilityใช้ง่าย เรียนรู้เร็วเจ้าหน้าที่ใหม่ใช้งานได้ภายใน 30 นาทีโดยไม่ต้องอบรม
Reliabilityน่าเชื่อถือ ทำงานต่อเนื่องระบบ available 99.5% ต่อเดือน
Performanceเร็วพอ ทรัพยากรพอค้นประวัติผู้ป่วยตอบภายใน 2 วินาที · รองรับ 500 ผู้ใช้พร้อมกัน
Supportabilityดูแลรักษา/ต่อยอดง่ายแก้รายการยาได้โดยแอดมินไม่ต้องแก้โค้ด · log ให้ทีม support

ตัวอย่างคำตอบเต็ม: FR / NFR ของ CS-Hospital (เอาแนวนี้ไปปรับเป็น CS-Pizza)

✅ Functional Requirements

  1. ระบบต้องบันทึก/แก้ไขข้อมูลผู้ป่วย (ประวัติรักษา, ผลรักษา, ผลห้องปฏิบัติการ)
  2. ระบบต้องเก็บข้อมูลบุคลากรทางการแพทย์ (แพทย์ พยาบาล ช่างเทคนิค)
  3. ระบบต้องค้นหาและแสดงประวัติการรักษาของผู้ป่วยตามรหัส/ชื่อ
  4. ระบบต้องออกรายงานได้ เช่น ใบรับรองแพทย์, ประวัติการรักษา (PDF)
  5. ระบบต้องส่งต่อผลวินิจฉัยไปยังทีมแพทย์เฉพาะทางผ่าน LINE หรือ Email
  6. ระบบต้องให้ผู้ใช้เข้าสู่ระบบด้วยบัญชีที่กำหนดสิทธิ์ตามบทบาท (แพทย์/พยาบาล/แอดมิน)

✅ Non-Functional Requirements

  1. (Security/FURPS) ข้อมูลผู้ป่วยต้องเข้าถึงได้เฉพาะผู้มีสิทธิ์ + เข้ารหัสข้อมูล + รหัสผ่านผิดเกิน 3 ครั้งถูกล็อก
  2. (Performance) ค้นหาประวัติผู้ป่วยต้องแสดงผลภายใน 2 วินาที รองรับผู้ใช้พร้อมกัน 500 คน
  3. (Reliability) ระบบต้องพร้อมใช้ 99.5% ต่อเดือน และกู้คืนข้อมูลจาก backup ได้ภายใน 1 ชม.
  4. (Usability) เจ้าหน้าที่ใหม่ใช้งานหน้าบันทึกผู้ป่วยได้ภายใน 30 นาที รองรับภาษาไทยและมือถือ
  5. (Supportability/Legal) เก็บ log การเข้าถึงข้อมูลผู้ป่วยทุกครั้งเพื่อตรวจสอบย้อนหลัง (PDPA)
ข้อผิดพลาดที่เสียคะแนนบ่อยเขียน "ระบบต้องเร็ว" "ใช้ง่าย" — เอ๊ะ เร็วแค่ไหน? ง่ายต่อใคร? → ต้องวัดได้ (measurable) เสมอ: มีตัวเลข เวลา เปอร์เซ็นต์ · และอย่าเขียนฟังก์ชันไปไว้ใน NFR (เช่น "ระบบต้องออกรายงาน" = FR ไม่ใช่ NFR!)

CS-Pizza แนวเดียวกัน: FR เช่น สั่งพิซซ่าออนไลน์/เลือกท็อปปิ้ง/ติดตามสถานะจัดส่ง/ชำระเงินออนไลน์/ประวัติคำสั่งซื้อ · NFR เช่น รับออเดอร์พร้อมกัน 1,000 ออเดอร์ช่วงค่ำ, แสดงสถานะภายใน 1 วินาที, ชำระเงินปลอดภัย (3-D Secure), ใช้ได้ทั้งมือถือ-คอม

Actorบทบาทภายนอกที่คุยกับระบบ (คน หรือ ระบบอื่น!) · Initiating (primary) = คนเริ่มใช้, Participating (secondary) = ช่วย/รับรู้ผล (แบ่งเป็น supporting = ช่วยทำงาน, offstage = ดูผลเฉย ๆ)ตุ๊กตาไม้ (stick figure)
Use Caseฟังก์ชันหนึ่งที่ระบบให้ ตั้งชื่อแบบ "กริยา + นาม"วงรี
System boundaryขอบเขตระบบสี่เหลี่ยมครอบ use case
«include»ทุกครั้งที่ทำ A ต้องทำ B เสมอ (ดึงพฤติกรรมร่วมมาใช้)ลูกศรเส้นทึบ + «include»
«extend»B ทำ "เพิ่ม" ในบางกรณีเท่านั้น (optional)ลูกศรเส้นทึบ + «extend»
Generalizationactor/use case สืบทอด (แพทย์ทั่วไป ← แพทย์เฉพาะทาง)ลูกศรสามเหลี่ยมโปร่ง
«include» vs «extend» คู่หลอกข้อสอบ «include»: จำเป็นเสมอ — "ส่งต่อผลให้ทีมเฉพาะทาง include ยืนยันตัวตน" (ไม่ยืนยัน = ส่งไม่ได้) ลูกศรชี้ออกจาก use case หลักไปหาตัวที่ถูก include
«extend»: เงื่อนไขบางครั้ง — "จัดการข้อมูลผู้ป่วย extend ด้วย แจ้งเตือนฉุกเฉิน" (เกิดเฉพาะเคสผู้ป่วยวิกฤต) · เคล็ดจำ: extend = พ่วงพิเศษ, include = แพ็กเกจบังคับ

6 · Schema for Detailed Use Case (แบบที่อาจารย์สอนใน Ch9)

เขียนตามเทมเพลตมาตรฐาน 7 บรรทัดนี้เป๊ะ ๆ Use Case UC-#: ชื่อ [กริยา+นาม] · Related Requirements: REQ ที่เกี่ยว · Initiating Actor: ใครเริ่ม · Actor's Goal: เป้าหมาย · Participating Actors: ใครช่วย/รับรู้ผล · Preconditions: ต้องจริงก่อนเริ่ม · Postconditions: ต้องจริงหลังจบ · + Flow of Events (Main Success + Extensions)

ตัวอย่างเต็ม: ส่งต่อผลวินิจฉัย

Use Case UC-5: ส่งต่อผลวินิจฉัย
Related Requirements: REQ-4
Initiating Actor: แพทย์
Actor's Goal: ส่งผลรักษาให้ทีม
  เฉพาะทางตรวจต่อ
Participating Actors: ระบบ LINE/Email
Preconditions: แพทย์ login แล้ว;
  มีผลวินิจฉัยในระบบแล้ว
Postconditions: ทีมเฉพาะทางได้รับ
  ผล + ระบบบันทึกประวัติส่ง

Flow of Events

Main Success Scenario:
→1. แพทย์เลือกผลวินิจฉัย + ทีมปลายทาง
 2. ระบบแสดงตัวอย่างเอกสาร
→3. แพทย์ยืนยันส่ง
 4. ระบบส่งผ่าน LINE/Email

Extensions:
3a. ช่องทางปลายทางล้มเหลว:
   ระบบแจ้ง + เก็บสถานะ "รอส่งซ้ำ"

→ = ฝั่ง actor ทำ, ไม่มี = ฝั่งระบบทำ · Extensions = กรณีผิดพลาด

7 · สถาปัตยกรรมซอฟต์แวร์ (Software Architecture) — ปี 67 เพิ่มมาเขียนตอบ

คำนิยามสั้น (เปิดคำตอบด้วยประโยคนี้) สถาปัตยกรรม = การตัดสินใจระดับสูงที่กำหนดโครงสร้างระบบ: มีคอมโพเนนต์อะไร ทำหน้าที่ใด และเชื่อมกันอย่างไร (connector) — เหมือนพิมพ์เขียวบ้าน ก่อนลงมือก่อน
สไตล์โครงเป็นอย่างไรเหมาะกับ
Client/ServerClient ส่งคำขอ → Server รอรับและตอบ ผ่าน connector (เครือข่าย)เว็บแอปทั่วไป
Central Repository (Database)ทุกซับซิสเต็มเขียน/อ่านผ่านคลังข้อมูลกลางระบบที่แชร์ข้อมูลเดียวกัน เช่น โรงพยาบาล
Layered (Multi-tier)แบ่งเป็นชั้น ๆ (UI → Application Logic → Technical Services) แต่ละชั้นใช้บริการชั้นล่าง · ลด coupling เพิ่ม reusabilityระบบองค์กรทั่วไป
MVCModel = ข้อมูล+logic · View = หน้าจอ · Controller = รับ input แล้วอัปเดต M/Vเว็บ/แอป UI ซับซ้อน
Pipe-and-Filterข้อมูลไหลผ่าน filter (ประมวลผลย่อย) ต่อกันด้วย pipeประมวลผลสายข้อมูล (UNIX shell, ETL)
Microservicesหยิบย่อยเป็นบริการเล็ก ๆ อิสระต่อกัน คุยผ่านเครือข่ายระบบใหญ่ scale แยกส่วนได้
P2P / RESTทุกโหนดเท่าเทียม / แบบ stateless บน HTTP สำหรับ web serviceแชร์ไฟล์ / API สมัยใหม่
สูตรเขียนตอบ "เขียนสถาปัตยกรรมซอฟต์แวร์ของระบบ" (เช่น CS-Pizza) ① เลือกสไตล์ + ให้เหตุผลผูกธุรกิจ ("เลือก Layered + Central Repository เพราะทุกฟังก์ชันแชร์ข้อมูลออเดอร์ชุดเดียวและทีมพัฒนาต้องแยก UI/logic") → ② วาดแผนภาพ (กล่องคอมโพเนนต์ + ลูกศร connector) → ③ อธิบายการไหล 1 รอบ ("ผู้ใช้สั่งพิซซ่า → UI ส่งคำขอ → Logic ตรวจสต็อก → บันทึก DB → ส่งงานครัว → UI อัปเดตสถานะ") → ④ บอกข้อดี/ข้อจำกัดที่ยอมรับ

8 · ศัพท์จับคู่สำรอง — Software Quality & Process Model (กันเผื่อออก)

Software Quality (Ch3)ความหมายแบบสั้นที่จับคู่ได้
Correctnessทำตาม functional spec ถูกต้องหรือไม่
Reliabilityความน่าจะเป็นที่ทำงานได้ตามคาดตลอดช่วงเวลาหนึ่ง
Robustnessทนต่อ input ประหลาด/สภาพผิดปกติ (ผู้ใช้มือใหม่กดอะไรก็ได้)
Performanceเร็วพอ ใช้ทรัพยากรพอ (ช้า → ลด productivity)
User Friendlinessใช้ง่ายสำหรับผู้ใช้เป้าหมาย (มือใหม่ → เมนู ไม่ใช่คำสั่ง)
Verifiabilityตรวจสอบได้ง่าย (ฝัง monitor เช็ก performance/correctness)
Maintainabilityแก้ไข/วิวัฒน์ต่อได้ง่าย (corrective/adaptive/perfective)
Repairabilityซ่อมง่ายเพราะโมดูลแยกชัด เปลี่ยน "ชิ้นส่วน" แทนทั้งก้อน
Reusabilityนำโมดูลกลับไปใช้ระบบอื่นได้
Portabilityย้ายไป platform/HW อื่นได้ง่าย
Understandabilityอ่าน-เข้าใจโค้ด/โครงสร้างได้ง่าย
Interoperabilityทำงานร่วมกับระบบอื่นได้ (แลกเปลี่ยนข้อมูล)
Process Model (Ch4/Ch8)จุดเด่นงานแบบไหนเหมาะ (โจทย์ชอบถาม)
Waterfallเรียงเป็นเส้นตรง เอกสารชัดความต้องการชัดแน่นอน ไม่ค่อยเปลี่ยน
Incrementalส่งมอบทีละส่วน (increment) ผู้ใช้เห็นเร็วอยากได้ของใช้เร็ว + ค่อยเพิ่มฟีเจอร์
Evolutionary/Prototypeทำต้นแบบไปเรื่อย ๆ จนความต้องการชัดความต้องการยังไม่ชัด
Spiralวนรอบ + ประเมินความเสี่ยงทุกรอบโครงการแพง/ความเสี่ยงสูง
Agileสปรินต์สั้น ๆ ยืดหยุ่น คุยกับลูกค้าถี่ความต้องการเปลี่ยนบ่อย ทีมเล็ก

1 · Process & fork() — ไล่โค้ดแบบมีจุดหลอก

1.1 พื้นฐานที่ต้องแม่นก่อน

Program vs Process: program คือไฟล์นิ่ง ๆ บนดิสก์ (เหมือนสูตรทำอาหาร) ส่วน process คือ "โปรแกรมที่กำลัง execute" (เหมือนการทำอาหารจริงตอนนี้ — มี PC ชี้ว่าทำถึงบรรทัดไหน, มี stack, มี data ของตัวเอง) เดียวกัน 1 สูตร แต่ทำพร้อมกันหลายเตาได้ = หลาย process

แนวคิดคืออะไรเปรียบเทียบ
Programไฟล์ executable บน disk (passive entity)สูตรอาหารเขียนไว้ในหนังสือ
Processprogram in execution (active entity) — มี program counter, stack, data sectionการลงมือทำอาหารตามสูตรนั้น ณ ตอนนี้
PCB (Process Control Block)"บัตรประจำตัว" ของ process เก็บ state, PC, registers, เลข PID — ใช้ตอน context switchล็อกเก็บของที่จดทุกอย่างไว้ พอกลับมาทำต่อได้เหมือนเดิม
Context Switchเซฟ state process เก่า + โหลด state ใหม่ — เป็น overhead (ทำงานจริง 0%)สลับงานระหว่าง 2 โต๊ะ ต้องเก็บของโต๊ะเก่าก่อน = เสียเวลา

1.2 กฎเหล็กของ fork() — จำ 3 บรรทัดนี้พอ

fork() = "เอาโปรแกรมนี้ ก๊อปตัวเองอีกชุด" pid_t pid = fork(); ถูกเรียก 1 ครั้ง แต่คืนค่า 2 ครั้ง (ในสอง process ที่กำลังรันอยู่):
  • ใน parent: คืน PID ของลูก (เลข > 0)
  • ใน child: คืน 0
  • ถ้าสร้างไม่สำเร็จ: คืน −1 (แต่ข้อสอบบอกว่าโค้ด compile ผ่านทุกข้อ ไม่ต้องสน)
ลูกได้ "สำเนา" ตัวแปรทั้งหมดของพ่อ (แก้ของใครของมัน ไม่เห็นกัน!) — ต่างจาก thread ที่แชร์ memory เดียวกัน

1.3 ตัวอย่างไล่มือ ที่ออกสอบตรง ๆ

ตัวอย่างที่ 1: fork ครั้งเดียว + if/else

int main() {
  pid_t pid;
  int i = 0;
  pid = fork();
  if (pid > 0) {        /* parent */
    i = 1;
    printf("I am parent i = %d\n", i);
  }
  else {                /* child */
    i = 2;
    printf("I am child i = %d\n", i);
  }
  return 0;
}
ผลการรันพิมพ์ออกมา 2 บรรทัดเสมอ: I am parent i = 1 และ I am child i = 2
เพราะเงื่อนไข pid>0 เป็นจริงเฉพาะใน parent, ใน child pid=0 จึงเข้า else · จุดหลอก: ลำดับบรรทัดไหนมาก่อนไม่แน่นอน (non-deterministic) — OS อาจให้ลูกรันก่อนก็ได้ แต่ว่าเนื้อความ 2 บรรทัดนี้ตายตัว

ตัวอย่างที่ 2: fork() 2 ครั้งติดกัน — นับ process (โจทย์โปรดอาจารย์)

fork();      /* จุด A */
fork();      /* จุด B */
printf("Hello\n");

นับแบบ "ต้นไม้"

เริ่มมี 1 process (P) · ผ่าน fork A → กลายเป็น 2 (P, C1) · ทั้งสองต่างคนต่างผ่าน fork B → แตกอีกทีละตัวเป็น 4 (P, C1, C2, C3) → Hello พิมพ์ 4 ครั้ง

สูตรเร็ว

fork() ติดต่อกัน n ครั้ง (ไม่มีเงื่อนไข) → process = 2ⁿ · printf = 2ⁿ บรรทัด · ถ้ามีเงื่อนไข if (pid==0) fork(); ต้องวาดต้นไม้ทีละกิ่ง ห้ามใช้สูตร
🚫 จุดหลอกยอดฮิตในข้อสอบ 1) ตัวแปร i ไม่แชร์กัน — ลูกได้สำเนา พ่อแก้ i=1 ลูกไม่เห็น (ถ้าโจทย์ให้พ่อแก้แล้วถามค่าในลูก ต้องตอบค่าเดิม) 2) printf อาจเพี้ยนเรื่อง buffer — ถ้าไม่มี \n ปลายข้อความ ข้อความอาจค้างใน buffer แล้ว "สำเนาติดไปกับลูก" ทำให้พิมพ์ซ้ำ (โค้ดที่ไม่มี \n = อย่าเพิ่งเชื่อว่าพิมพ์ครบตามจำนวน) 3) fork ในลูป for(i=0;i<3;i++) fork(); → 1+2+4+8 = 15 ลูกรวม 16 process (2³) 4) แถวลำดับการพิมพ์ parent/child สลับได้ — ข้อที่ถาม "ลำดับแน่นอน" มักเป็นเท็จ

2 · exec() / wait() / exit() — สี่เหลี่ยมคู่ใจของ shell

แพทเทิร์นคลาสสิกที่อาจารย์สอนและออกบ่อย: พ่อ fork → ลูก exec (เปลี่ยนร่างเป็นโปรแกรมอื่น) → พ่อ wait รอลูกจบ

pid_t pid = fork();
if (pid < 0) { fprintf(stderr, "Fork Failed"); exit(-1); }
else if (pid == 0) {          /* ลูก */
  execlp("/bin/ls", "ls", NULL);   /* เปลี่ยนร่างเป็นคำสั่ง ls */
}
else {                        /* พ่อ */
  wait(NULL);                      /* รอลูกจบก่อน */
  printf("Child Complete");
  exit(0);
}
ฟังก์ชันทำอะไรจุดที่ออกสอบ
exec() ตระกูล execlp/execvp…แทนที่ process image ปัจจุบันด้วยโปรแกรมใหม่ — PID เดิม ไม่สร้าง process ใหม่!โค้ดหลัง exec ในสายเดียวกัน "ไม่มีวันรัน" ถ้า exec สำเร็จ · ลูก exec แล้วจำนวน process ไม่เพิ่ม
wait(&status) / waitpid(pid,…)พ่อหยุดรอ (block) จนลูกหนึ่งตัว/ตัวที่ระบุจบ แล้วเก็บ exit statusถ้าพ่อ wait ก่อนลูกจบ → พ่อนอนรอ · ลูกจบแล้วพ่อยังไม่ wait → ลูกกลายเป็น zombie
exit(status)จบ process ส่ง status ให้พ่อผ่าน wait · OS เคลียร์ทรัพยากรทั้งหมดพ่อตายก่อนลูก → ลูกเป็น orphan (บาง OS ทำ cascading termination ฆ่าลูกตาม)
จำ 3 คำนี้ให้ได้Zombie = ลูกตายแล้วแต่พ่อยังไม่ wait (ศพยังไม่ถูกเก็บ) · Orphan = พ่อตายก่อนลูก · Cascading termination = พ่อถูกยกเลิกแล้ว OS ฆ่าลูกทั้งวงตาม

3 · CPU Scheduling — โจทย์คำนวณที่ออกทุกปี

3.1 ค่าที่ต้องคำนวณ (สูตรเดียวจบ)

Turnaround Time (TAT) = Completion − Arrival  ·  Waiting Time (WT) = TAT − Burst Time
เปรียบเทียบ: เข้าคิวร้านก๋วยเตี๋ยวตอน 9:00 ได้ข้นตอน 9:40 → TAT = 40 นาที (รอ+ทำ) · ถ้าทำจานใช้ 10 นาที → WT = 40−10 = 30 นาที (เวลา "ยืนรอเปล่า ๆ")

3.3 SJF (Shortest Job First) — งานสั้นทำก่อน

เหมือนเห็นลูกค้าซื้อของชิ้นเดียวให้แซงคิว (ประสิทธิภาพเฉลี่ยดีสุด แต่ต้องรู้ burst ล่วงหน้า ซึ่งในโจทย์เขาให้มา) · Non-preemptive: จบ burst ปัจจุบันก่อนค่อยเลือกใหม่

4 · IPC — Signal, Pipe, Shared Memory (บท Final ชุดแรก)

Process สองตัวจะคุยกันได้ด้วย 3 วิธีหลักใน UNIX ที่อาจารย์สอน: Signal, Pipe, Shared Memory

4.1 Signal — "เคาะไหล่"แบบส่งข่าวสั้น

Signal = software interrupt บอกว่า "เกิดเหตุการณ์แล้ว" พกข้อมูลน้อยมาก (แค่เลข signal) เหมือนกริ่งดัง — รู้ว่า "มีเรื่อง" แต่ไม่ได้บอกรายละเอียด · Process รับแล้วเลือกได้ 3 อย่าง: catch (ตั้ง handler เอง), ใช้ default ของ OS, หรือ mask/block (พักสัญญาณไว้ก่อน)

Signalเกิดจากจำง่าย
SIGINTผู้ใช้กด Ctrl+CINT = interrupt
SIGFPEหารด้วยศูนย์ / overflowFPE = Floating Point Exception
SIGTERMขอให้จบแบบสุภาพ (default ของคำสั่ง kill)TERM = terminate
SIGQUITCtrl+\QUIT
SIGUSR1/2ผู้ใช้กำหนดเองUSR = user
SIGKILLสั่งฆ่าทันที — catch/ignore ไม่ได้!เลข 9 → kill -9 pid
signal(SIGINT, handler);   /* ติดตั้ง handler: เจอ SIGINT เรียก handler(int sig) */
raise(SIGTERM);            /* ส่ง signal ให้ "ตัวเอง" */
kill(pid, SIGUSR1);        /* system call ส่ง signal ให้ "process อื่น" */
/* shell: kill -9 1234 = ส่ง SIGKILL (เลข 9) ให้ pid 1234; ไม่ใส่ชื่อ = SIGTERM */

4.2 Pipe — ท่อส่งข้อมูลทางเดียว

pipe(pfd) ก่อน fork

ได้ fd คู่หนึ่ง · ห้ามสลับลำดับ! ถ้า fork ก่อนแล้วค่อย pipe พ่อลูกจะไม่เห็นท่อเดียวกัน

fork() → ทั้งสองได้สำเนา fd

หลัง fork มี 2 read-ends + 2 write-ends (ทุกคนเขียน/อ่านได้หมด = วุ่น)

ปิดปลายที่ไม่ใช้

ผู้ส่ง (พ่อ) close(pfd[0]) · ผู้รับ (ลูก) close(pfd[1]) → เหลือทางเดินข้อมูลชัดเจนทางเดียว

เขียน/อ่านด้วย write/read

write(pfd[1], buf, size) และ read(pfd[0], buf, SIZE) · ถ้าท่อว่าง read จะ block รอข้อมูล
แล้ว ls | wc ทำงานยังไง? (เข้าใจตรงนี้ = เข้าใจ dup2) shell สร้าง pipe แล้ว fork 2 ตัว · ตัวที่จะกลายเป็น ls ต้องเขียนลง pipe แต่ ls เขียนที่ stdout (fd 1) เท่านั้น → ใช้ dup2(pfd[1], 1) คัดลอก fd ท่อไปทับตำแหน่ง 1 (stdout ชี้เข้าท่อ) · ฝั่ง wc ใช้ dup2(pfd[0], 0) ให้ stdin อ่านจากท่อ · แล้วปิด fd เดิม (3, 4) ที่ไม่ใช้ — dup2 = "ตั้งชื่อเล่นใหม่ให้ไฟล์/ท่อ"

Producer ทำ count++, Consumer ทำ count-- พร้อมกัน แต่ภาษาเครื่องของ count++ แยกเป็น 3 คำสั่ง! สมมติ count = 5:

เงื่อนไขทางออกที่ดีต้องมี 3 อย่าง (เติมคำออกบ่อย) 1) Mutual Exclusion — ครั้งละ 1 process ใน critical section · 2) Progress — ถ้าว่างและมีคนอยากเข้า ต้องเลือกใครสักคนเข้า ห้ามลังเลไม่จบ · 3) Bounded Waiting — มีลิมิตจำนวนรอบที่คนอื่นแซงได้ก่อนถึงรอบเรา (ไม่มีของรายตาย)

Peterson's Solution (กรณี 2 process): ใช้ turn (ถึงคิวใคร) + flag[2] (ใครอยากเข้า): flag[i]=TRUE; turn=j; while(flag[j] && turn==j); → คนที่อยากเข้าประกาศตัว แล้วยกคิวให้อีกตัวก่อน ถ้าอีกตัวไม่อยากเข้าหรือถึงคิวเรา ก็เข้าได้

Bakery Algorithm (n process): เหมือนจับเลขคิวร้านขนม — ทุกคนจับเลข = max ที่มี +1 คนเลขน้อยเข้าก่อน เลขซ้ำใช้ PID ตัด ((เลข, pid) เรียงพจนานุกรม)

5.2 Semaphore — จราจรของ process

Semaphore S = ตัวนับ int ที่แก้ได้ด้วย 2 คำสั่ง atomic เท่านั้น wait(S) (เดิมชื่อ P) = ขอเข้า: ถ้า S ≤ 0 นั่งรอ, ได้แล้ว S−− · signal(S) (เดิมชื่อ V) = ปล่อย: S++
เปรียบเทียบ: S = จำนวนตั๋วเข้าสนาม — มีตั๋ว (S>0) หยิบเข้าไปได้ (S ลด) · ตั๋วหมด (S=0) ต้องรอคนออกคืนตั๋ว (S เพิ่ม)

Binary semaphore (mutex)

S มีค่า 0 หรือ 1 = กุญแจห้องน้ำ 1 ดอก · ใช้: wait(S); critical section; signal(S); เริ่มต้น S = 1

Counting semaphore

S เป็นจำนวนเต็มกว้าง ๆ = ที่จอดรถ n ช่อง · เริ่ม S = N, เข้าจอด 1 คัน S−− ออก 1 คัน S++

ปัญหาคลาสสิก 3 ตัว (จะเขียนโค้ดให้ได้)

① Bounded Buffer (ผู้ผลิต-ผู้บริโภค)

Buffer N ช่อง · ใช้ 3 semaphore: mutex=1 (กุญแจ buffer), full=0 (ของในถัง), empty=N (ที่ว่าง)

/* Producer */
while(true){
  ผลิตของ;
  wait(empty);  wait(mutex);
  ใส่ของลง buffer;
  signal(mutex); signal(full);
}
/* Consumer */
while(true){
  wait(full);  wait(mutex);
  หยิบของออก;
  signal(mutex); signal(empty);
  ใช้ของ;
}

อ่านทางไหน: empty/full คือ "ตั๋วที่ว่าง/ของสด" · mutex คุมอย่าเติม-ตักพร้อมกัน · ลำดับ wait สลับไม่ได้! (wait mutex ก่อน empty → deadlock)

② Readers–Writers

หลายคนอ่านพร้อมกันได้ แต่เขียนต้องอยู่คนเดียว · ตัวแปร: readcount=0, mutex=1 (คุม readcount), wrt=1 (กุญแจเขียน)

/* Writer */
wait(wrt);
  เขียน;
signal(wrt);

/* Reader */
wait(mutex);
  readcount++;
  if (readcount == 1) wait(wrt);
signal(mutex);
  อ่าน;
wait(mutex);
  readcount--;
  if (readcount == 0) signal(wrt);
signal(mutex);

ผู้อ่านตัวแรก (readcount==1) เป็นคน "ล็อกประตูเขียน" ตัวสุดท้าย (readcount==0) เป็นคนปลดล็อก

③ Dining Philosophers (5 คน 5 ตะเกียบ)

นักปราชญ์ i ต้องได้ตะเกียบสองข้าง: chopstick[i] (ขวามือ) และ chopstick[(i+1)%5] (ซ้ายมือ) — เริ่มทุกอัน = 1

กิน;

ถ้าทุกคนหยิบขวาพร้อมกันสำเร็จ แล้วรอซ้ายตลอดกาล = deadlock! (ทุกคนถือตะเกียบ 1 อันแล้วรออีกข้าง) — โยงต่อเนื้อหา deadlock

ข้อผิดพลาดคลาสสิกของ semaphore (ออกถูก/ผิด)1) signal(mutex) … wait(mutex) — สลับลำดับ ทำให้ mutual exclusion พัง · 2) wait(mutex) … wait(mutex) — ล็อกสองที = รอตัวเอง (deadlock) · 3) ลืม wait หรือลืม signal ไปเลย

7 · Deadlock — สี่เงื่อนไข, Banker's Algorithm (คำนวณออกแน่)

Deadlock = process ≥ 2 ตัว รอซึ่งกันและกันตลอดกาล · ภาพจำจากสไลด์: สะพานทางเดียว — รถวิ่งสวนกันคนละฝั่ง ต่างยึดช่วงสะพานของตัวเองแล้วรออีกฝั่งถอย แต่ไม่มีใครถอย = ตัน

4 เงื่อนไขต้องครบพร้อมกันถึงเกิด deadlock (เติมคำ 100%) 1) Mutual Exclusion — resource ใช้ร่วมกันไม่ได้ · 2) Hold and Wait — ถือของไว้แล้วขอเพิ่ม · 3) No Preemption — ตัดของจากกันไม่ได้ ต้องรอเจ้าของคืนเอง · 4) Circular Wait — รอเป็นวงกลม
ตัดวงจรข้อใดข้อหนึ่งออก = ไม่เกิด deadlock (นี่คือหัวใจของ Prevention)

7.1 Resource-Allocation Graph (RAG)

จุดวงกลม = process (P), จุดสี่เหลี่ยม = resource (R, มีได้หลาย instance) · ลูกศร P → R = กำลังขอ (request edge), R → P = กำลังถือ (assignment edge)

กฎการอ่านกราฟ (ถูก/ผิดออกบ่อย) ไม่มีวงจร (no cycle) → ไม่มี deadlock แน่นอน · มีวงจร → ถ้าทุก resource มีinstance เดียว = deadlock แน่ · ถ้ามีหลาย instance = "อาจ" deadlock (ยังไม่ตัดสิน ต้องเช็กต่อ)

7.2 3 กลยุทธ์จัดการ deadlock

1. Prevention (ป้องกันโครงสร้าง)

ออกแบบให้ 4 เงื่อนไขขาดข้อใดข้อหนึ่ง ตั้งแต่วิธีขอ resource

2. Avoidance (เลี่ยงขณะรัน)

รู้ข้อมูลล่วงหน้า (max need) → ตรวจทุกครั้งก่อนอนุมัติ อย่าให้เข้า unsafe state

3. Detection + Recovery

ปล่อยเกิดก่อน ค่อยหาวงจรแล้วแก้ (abort/preempt) — สิ่งที่ UNIX เลือก: ทำเมิน (ostrich)

Prevention ตัดข้อไหนวิธีทำผลข้างเคียง
Mutual Exclusionทำให้ resource แชร์ได้ (ทำได้เฉพาะของแชร์ได้ เช่น read-only)ของจำพวก exclusive ทำไม่ได้
Hold and Waitขอครบทุกอย่างก่อนเริ่มงาน หรือขอได้เมื่อมือเปล่าเท่านั้นใช้ resource ต่ำ · starvation
No Preemptionขอแล้วไม่ได้ ต้องคืนของที่ถือทั้งหมด ไปขอใหม่รอบหน้างานเดิมเสียเวลาเริ่มใหม่
Circular Waitจัดลำดับเลข resource แล้วขอตามลำดับขึ้นเท่านั้น (ทำได้จริงที่สุด)ต้องออกแบบลำดับดี ๆ

8 · Real Memory — Fragmentation, Paging, EAT (ออกคำนวณหนักสุด!)

8.1 Logical vs Physical Address + MMU

ตัวอย่างเฉลยละเอียด: หลุม 100K, 500K, 200K, 300K, 600K — งาน 212K จะลงหลุมไหน? First-fit → 100K ไม่พอ → 500K (พอ) เอาเลย เหลือ 288K · Best-fit → ไล่ดูทุกหลุม: พอหมดยกเว้น 100K → เลือกที่ "เหลือน้อยสุด" = 300K (เหลือ 88K) · Worst-fit → 600K (เหลือ 388K)

8.3 Paging — หัวใจข้อคำนวณ Final ⭐

แนวคิดตัด logical memory เป็นหน้าขนาดเท่ากัน (page) และ physical เป็นกรอบขนาดเท่ากัน (frame) แล้วหน้าไหนว่างก็วางกรอบไหนก็ได้ — จบปัญหา external fragmentation · แต่หน้าสุดท้ายมักไม่เต็ม = internal fragmentation เล็ก ๆ (เฉลี่ยครึ่งหน้า)
โจทย์คำนวณ Paging — ทำตามได้ = ได้คะแนน (รุ่นพี่บอกว่า "คนส่วนมากไม่ทัน") โจทย์: page size = 1 KB (2¹⁰ bytes), logical address space = 16 bits (2¹⁶), ถามหา physical address ของ logical 2500 โดย page table บอกว่า page ที่ p อยู่ใน frame 7
วิธี 4 ขั้น (ท่องได้ = ทันแน่):
① หา n: page size 1K = 2¹⁰ → offset ใช้ 10 บิตล่าง
② แปลง 2500 เป็นฐานสอง: 2500 = 10 0111 0000 0100 (16 บิต)
③ ซ้าย/ขวาแยก: p = 10 0111 (บิตบน 6 บิต) = 39, d = 100000100 = 516 (ตรวจ: 39×1024 + 516 = 40532 ✓)
④ ประกอบ: physical = frame# × page size + d = 7 × 1024 + 516 = 7684
เทคนิคประหยัดเวลา: d = address mod 1024, p = address div 1024 — ใช้เครื่องคิดเลขแทนการแปลงฐานสองก็ได้!

TLB และ Effective Access Time (สูตรออกเติมคำ/คำนวณ)

เข้าถึงข้อมูล 1 ครั้งแบบมี page table = ต้องไป RAM 2 รอบ (รอบแรกอ่าน page table หา frame, รอบสองอ่านข้อมูลจริง) → ช้า! จึงมี TLB (associative cache เก็บ p→frame ที่ใช้ล่าสุด เหมือนจดเบอร์โทรคนที่โทรบ่อยไว้ในมือ)

สูตร EAT (จากสไลด์: memory access = 1 μs, TLB lookup = ε) EAT = α(1 + ε) + (1 − α)(2 + ε) โดย α = hit ratio
ถ้า ε เล็กมากจนมองข้าม: EAT = 2 + ε − α (จำ: ยิ่ง hit เยอะ ยิ่งเข้าใกล้ 1 รอบ)
ตัวอย่าง: α = 80%, ε ≈ 0 → EAT = 0.8(1) + 0.2(2) = 1.2 μs (เร็วขึ้นจาก 2 รอบชัดเจน)

เรื่องเสริมที่ออกถูก/ผิด

  • Valid/invalid bit — v = หน้านี้อยู่ใน address space ของ process (ใช้ได้), i = ไม่อยู่ (อย่าไป — ถ้าไปจะ trap เป็น page fault)
  • Two-level page table — page table ใหญ่เกินจึงหักเป็นตารางสองชั้น (เหมือนเลขหน้าหนังสือแบบ "บท→หน้า")
  • Segmentation — แบ่งตามความหมายโปรแกรมเมอร์: main, function, stack, symbol table… address = <segment, offset> ตารางเก็บ base + limit (limit เกิน → ตรวจ error) — paging แบ่งตามขนาด, segmentation แบ่งตามความหมาย

9.3 Thrashing & Working Set & Locality (เรื่องทฤษฎีที่ Final ชอบออก)

Thrashing = กวาดหน้าขึ้น-ลงจนเวลาใช้ไปหมดกับ swapping process มีหน้าไม่พอ → page fault ถี่มาก → CPU ว่าง → OS เข้าใจว่า "มีคนใช้ CPU น้อย" → เพิ่ม process เข้ามาอีก → RAM ยิ่งแน่น → fault ยิ่งเยอะ (วงจรบ้าความคิด) · ผล: CPU utilization ดิ่ง
แก้ด้วย Working-Set Model: สังเกตหน้าที่ใช้ในช่วง Δ (working-set window) แล้วให้ RAM พอสำหรับรวม working set ของทุก process: D = Σ WSSᵢ ถ้า D > m → suspend process บางตัวออก

Locality of Reference = โปรแกรมมักอ้าง address กระจุก ๆ ด้วยกัน (ลูปใช้แถวเดียวกันซ้ำ ๆ) — เป็นเหตุผลที่ LRU เวอร์ · ตัวอย่างจากสไลด์ int[128][128] แถวละ 1 page:

❌ ลูปวนเก่

for (j = 0; j < 128; j++)
  for (i = 0; i < 128; i++)
    data[i][j] = 0;

กระโดดข้ามแถวทุกก้าว → 16,384 page faults

✅ ลูปวนช้า (แถวต่อแถว)

for (i = 0; i < 128; i++)
  for (j = 0; j < 128; j++)
    data[i][j] = 0;

ใช้หน้าเดียวจนหมดก่อนย้าย → 128 page faults (น้อยลง 128 เท่า!)

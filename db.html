[2] Normalization — 40 คะแนน (กินครึ่งข้อสอบ) ⭐

2.1 พื้นฐานที่ต้องรู้ก่อนเข้า NF

Functional Dependency (FD)

X → Y อ่านว่า "X กำหนด Y" = รู้ค่า X ตัวเดียวก็รู้ค่า Y แน่นอน เช่น รหัสนักศึกษา → ชื่อ · เหมือนเลขบัตรประชาชน → ชื่อ-เกิด (เลขเดียวกัน = คนเดียวกัน)

Prime / Non-prime attribute

Prime = attribute ที่เป็นส่วนของ candidate key ใด ๆ · Non-prime = ที่เหลือ · กฎ 2NF/3NF พูดถึง non-prime ทั้งคู่!

2.2 บันได 6 ขั้น — แต่ละขั้น "แก้อาการ" อะไร

ตารางตัวอย่างใช้ร่วมทั้งบท: ใบสั่งซื้อ

OrderIDProductIDProductNameQtyCustomerNameCustomerPhone (หลายเบอร์)
O1P1Mouse2Somchai081-xxx, 089-yyy
O1P2Keyboard1Somchai081-xxx, 089-yyy
O2P1Mouse1Suda092-zzz

1NF — ทุกช่องต้องเป็นค่าเดี่ยว (atomic) ไม่มี repeating group

แก้: แยกเบอร์โทรออกเป็นแถวละ 1 เบอร์ (หรือตารางใหม่) — key รวม (OrderID, ProductID) · เปรียบเทียบ: ที่จอดรถต้องจอดทีละคัน ห้ามจอด 2 คันในช่องเดียว

2NF — อยู่ใน 1NF + ไม่มี partial dependency

ปัญหา: ProductName ขึ้นกับ ProductID ตัวเดียว (ส่วนหนึ่งของ key รวม) → แยกตาราง Product(ProductID, ProductName) ออก · เปรียบเทียบ: key รวมคือคู่แต่งงาน แต่ข้อมูลบางอย่างรู้จัก "คนเดียว" ก็พอ — ของที่รู้จากคนเดียวให้แยกบ้าน

3NF — อยู่ใน 2NF + ไม่มี transitive dependency

สมมติมี CustomerID → City → ShippingFee (รู้จังหวัดก็รู้ค่าส่ง) — ShippingFee ขึ้นกับ City ที่ไม่ใช่ key → แยกตาราง City(City, ShippingFee) · สูตรจำ: "non-key ห้ามกำหนด non-key ด้วยกัน"

2.3 BCNF — เวอร์ชันเข้มของ 3NF (ข้อต่างเป็นโจทย์โปรด)

3NF vs BCNF ต่างกันยังไง (ตอบสั้น ๆ ตรงนี้ได้คะแนน) 3NF: ทุก FD X → A ต้องมี (ก) X เป็น superkey หรือ (ข) A เป็น prime attribute — ให้อภัยกรณีที่ตัวถูกกำหนดเป็น prime
BCNF: เข้มขึ้น — ทุก determinant ต้องเป็น superkey เท่านั้น ไม่มีข้อยกเว้น
ตัวอย่างคลาสสิก: ตาราง (Student, Subject, Teacher) กฎ "อาจารย์ 1 คน สอน 1 วิชา" (Teacher → Subject) และ "นักศึกษา 1 คนต่อวิชา มีอาจารย์คนเดียว" ({Student, Subject} → Teacher) → Teacher กำหนด Subject แต่ Teacher ไม่ใช่ candidate key → 3NF ผ่าน (Subject เป็น prime) แต่ BCNF ไม่ผ่าน → ต้องแยก (Student, Teacher) กับ (Teacher, Subject)

2.4 4NF — จัดการ Multi-valued Dependency

เกิดเมื่อตารางมีข้อมูลอิสระสองชุดที่หลายค่า อยู่รวมกัน เช่น พนักงานคนเดียวมีหลาย skill และ (อิสระจากกัน) พูดได้หลายภาษา:

EmployeeSkillLanguageปัญหา
AnnSQLไทยต้องเก็บแบบ cross product: 2 skills × 2 ภาษา = 4 แถว ซ้ำ ๆ · เพิ่มภาษาใหม่ 1 ภาษาต้องใส่ครบทุก skill → update anomaly
AnnSQLอังกฤษ
AnnJavaไทย

4NF: อยู่ใน BCNF + ไม่มี nontrivial multivalued dependency (ยกเว้น determinant เป็น superkey) → แก้ด้วยการแยกเป็นสองตาราง: (Employee, Skill) และ (Employee, Language) · เปรียบเทียบ: ข้อมูลสองเรื่องที่ "ไม่เกี่ยวกันเลย" ห้ามบังคับให้เกิดเป็นคู่ — แยกสมุดจดสองเล่ม

2.5 5NF — Join Dependency (ขั้นสูงสุด)

ตารางถูกแบ่งย่อยได้เป็น 3 ตารางขึ้นไป แล้ว join กลับมาได้ข้อมูลเดิมพอดี โดยไม่มีแถวหลอน (spurious tuples) ที่ไม่ควรเกิด · เงื่อนไขคลาสสิก: ตาราง (Dealer, Product, Customer) ที่มีกฎสามเส้นทาง "ดีลเลอร์ขายสินค้าอะไร" + "ลูกค้าซื้อจากดีลเลอร์ไหน" + "ลูกค้าซื้อสินค้าอะไร" ครบสามชุด → เก็บแยก 3 ตาราง แล้ว join กลับจะยังตรงความจริงธุรกิจ · ถ้าแบ่ง 2 ตารางแล้ว join กลับเกิดแถวเก๊ = ยังไม่ผ่าน 5NF

สูตรตอบข้อ Normalization ในข้อสอบ (เขียนตามนี้ทุกข้อ) ① ระบุ key และ FD ทั้งหมดก่อน → ② ชี้ "อาการ" ที่ผิดระดับ NF นั้น (partial/transitive/multivalued) พร้อมเขียน FD ที่ผิด → ③ แสดงการแยกตาราง (เขียน schema ใหม่ + กำกับ key) → ④ ตรวจว่าแต่ละตารางผ่านระดับนั้นแล้ว และ join กลับได้ข้อมูลเดิมไม่หายไม่เกิน (lossless join)

[3] Transaction Processing — Recovery + Concurrency (30 คะแนน) ⭐

3.1 Transaction & ACID (พื้นฐานต้องพิมพ์ได้)

Transaction = หน่วยงานเชิงตรรกะที่ต้อง "สำเร็จทั้งหมดหรือไม่ทำเลย" เหมือนโอนเงิน: หักบัญชี A + เพิ่มบัญชี B ต้องเกิดคู่กัน — หักแล้วระบบล่มก่อนเพิ่ม = โลกพัง จึงต้อง ROLLBACK
ACIDแปลว่าตัวอย่าง (โอนเงิน)
Atomicityทำครบทั้งหน่วยหรือไม่ทำเลยหัก A แล้วเพิ่ม B ต้องสำเร็จทั้งคู่ ไม่งั้นยกเลิกทั้งคู่
Consistencyก่อน-หลัง transaction ฐานข้อมูลถูกต้องตามกฎเสมอผลรวมเงิน A+B เท่าเดิมทุกครั้ง
Isolationtransaction พร้อมกันไม่แทรกกันจนงงคนอื่นไม่ควรเห็นสถานะ "หักแล้วยังไม่เพิ่ม" ค้าง ๆ
Durabilitycommit แล้วข้อมูลอยู่จริงแม้ไฟดับโอนเสร็จ ไฟดับ เงินก็ยังเข้าบัญชี B

3.2 Recovery Control — Log-based Recovery (ออก "ทำ log rollback เหมือนในสไลด์")

Recovery = ทำให้ DB กลับสู่สถานะถูกต้องหลังพัง (crash) · เครื่องมือหลักคือ log file — จดทุกการเปลี่ยนแปลงลง log ก่อนแตะข้อมูลจริง (WAL: Write-Ahead Log เหมือนจดใบเสร็จไว้ก่อนเอาของออกจากคลัง)

<T1, start>
<T1, X, 100, 200>      /* T1 เปลี่ยน X: เดิม 100 → ใหม่ 200 (จด old & new value) */
<T1, Y, 50, 80>
<T1, commit>

Deferred Update (เขียนเมื่อ commit แล้ว)

เก็บเขียนไว้ที่ log ก่อน รอ commit ค่อยลง DB จริง
พังก่อน commit → ไม่ต้องทำอะไร (DB ยังไม่เปลี่ยน) · พังหลัง commit → REDO จาก log

Immediate Update (เขียนทันทีได้)

เขียนลง DB ได้ก่อน commit
พังก่อน commit → UNDO (ใช้ old value คืน) · พังหลัง commit → REDO (ใช้ new value)

ตัวอย่างไล่ rollback ตามสไลด์ (checkpoint)

กรณี (หลัง crash)สถานะตาม logต้องทำอะไร
T1commit ก่อน checkpointไม่ต้องทำอะไร (เขียนถึง disk แล้ว)
T2start ก่อน checkpoint, commit หลัง crash ไม่ทันUNDO (คืน old value ทุก item)
T3start ก่อน checkpoint, commit หลัง checkpoint ก่อนพังREDO (เผื่อเขียนไม่ครบ disk)
T4start หลัง checkpoint ไม่มี commitUNDO

Checkpoint = จุดถ่ายรูป: ล้านข้อมูลค้างจาก buffer ลง disk + จดใน log — พังแล้วไม่ต้องไล่ log ตั้งแต่ต้น (เหมือนเซฟเกมเป็นระยะ)

3.3 Concurrency Control — ปัญหา + วิธีคุม (2 ข้อใหญ่!) ⭐

Concurrency Control = เทคนิคคุม transaction หลายตัวที่รันพร้อมกันให้ผลลัพธ์เหมือน "รันเรียงกันตัวต่อตัว" (serializable) โดยไม่ทำให้ข้อมูลเสีย

ปัญหาคลาสสิก 4 อาการ (เห็นตารางไทม์ไลน์แล้วต้องเรียกชื่อได้)

อาการเกิดยังไง (ไทม์ไลน์)เหมือน
Lost UpdateT1 อ่าน X=100 → T2 อ่าน X=100 → T1 เขียน 110 → T2 เขียน 120 → ผลสุดท้าย 120 หายไป 10 ที่ T1 เพิ่มสองคนแก้ไฟล์ Google Doc จากของเก่าทั้งคู่ ของคนแรกถูกทับ
Dirty ReadT1 เขียน X=200 ยังไม่ commit → T2 อ่าน 200 ไปใช้ → T1 rollback กลับ 100 → T2 ใช้ค่าปลอมซื้อของตามป้ายราคาที่พนักงานยังไม่ยืนยัน สุดท้ายราคาถูกยกเลิก
Unrepeatable ReadT1 อ่าน X=100 → T2 เปลี่ยน X=200 + commit → T1 อ่านซ้ำได้ 200 ≠ 100ดูราคาวันนี้ 100 นาทีเดียวกลับมาดูใหม่กลายเป็น 200
Phantom ReadT1 นับแถว "ออเดอร์วันนี้" ได้ 10 → T2 insert ออเดอร์ใหม่ + commit → T1 นับซ้ำได้ 11นับคนในห้อง 10 คน มีคนเดินเข้ามา กลายเป็น 11 (ผีเพิ่มแถวใหม่)

วิธีคุม 3 แบบหลัก

① Locking (2PL)

อ่าน = Shared lock (คนละคนได้) · เขียน = Exclusive lock (คนเดียว) · Two-Phase Locking: ช่วง growing (ล็อกได้เรื่อย ๆ ปลดไม่ได้) → ช่วง shrinking (ปลดได้อย่างเดียว ล็อกใหม่ไม่ได้) — การันตี serializable · ข้อเสีย: เกิด deadlock ได้ (รอ lock กัน)

② Timestamp Ordering

จ่ายเลขคิว (timestamp) ให้แต่ละ transaction · ถ้า T เก่ากว่าพยายามเขียนทับข้อมูลที่ "คนคิวใหม่เขียนไปแล้ว" → ผิดลำดับ → rollback ทั้ง transaction แล้วเริ่มใหม่ (ไม่มี lock ไม่มี deadlock แต่ต้องยอม restart)

③ Optimistic (Validation)

เชื่อว่าชนกันน้อย: อ่าน-ทำงานเงียบ ๆ ก่อน → ตอนจบค่อยตรวจว่าชนใครไหม → ไม่ชนค่อย commit, ชน = rollback · เหมาะกับงานอ่านเยอะ

สูตรตอบข้อ Concurrency Control (2 ข้อใหญ่ 30 คะแนน) ① นิยาม: "เทคนิคจัดการ transaction พร้อมกันหลายตัวให้ผลเหมือนรันเรียงกัน (serializable) ป้องกัน lost update / dirty read / unrepeatable read / phantom" → ② อธิบายกลไกที่เลือก (เช่น 2PL: shared/exclusive lock + 2 เฟส) → ③ ยกตัวอย่างไทม์ไลน์ T1/T2 พร้อมตารางเวลา แสดงว่าโดยไม่คุมเกิดอาการไหน และเมื่อใช้ล็อกแล้วจังหวะไหนรอ/สำเร็จ → ④ สรุปผลว่าคุณสมบัติใดถูกรักษา

Star Schema vs Snowflake Schema (รู้ความต่าง — ไม่ต้องออกแบบ)

Star Schema ⭐

Fact ตรงกลาง + Dimension ล้อมรอบ เชื่อมตรง ๆ ทุกอัน — dimension ไม่แตกย่อย · JOIN น้อย คิวรีไว · โครงง่าย

Snowflake Schema ❄️

dimension ถูกปรับให้เป็นปกติ (normalized) แตกเป็นตารางย่อย เช่น Product → Category → หมวดใหญ่ · ลดซ้ำซ้อนใน dimension แต่ JOIN เพิ่ม คิวรีช้าลง

6.2 JOIN ทั้งหมด + ผลลัพธ์จริง ⭐

-- INNER JOIN: เอาเฉพาะคู่ที่ตรงกัน (คนอื่นหายหมด)
SELECT c.ชื่อ, o.OrderID, o.ยอด
FROM Customers c INNER JOIN Orders o ON c.ID = o.CustID;

-- LEFT OUTER JOIN: ลูกค้าทุกคนต้องโผล่ แม้ไม่เคยสั่ง (Suda ต้องมี!)
SELECT c.ชื่อ, o.OrderID
FROM Customers c LEFT JOIN Orders o ON c.ID = o.CustID;

-- FULL OUTER JOIN: ทั้งสองฝั่งครบ (รวม Order A4 ที่ไม่มีเจ้าของด้วย)
SELECT c.ชื่อ, o.OrderID
FROM Customers c FULL OUTER JOIN Orders o ON c.ID = o.CustID;
ชนิดผลลัพธ์ (ชื่อ · OrderID)จุดสังเกต
INNERSomchai·A1, Somchai·A2, Mana·A33 แถว · Suda หาย, A4 หาย
LEFTSomchai·A1, Somchai·A2, Suda·NULL, Mana·A34 แถว · ฝั่งลูกค้าครบ — โจทย์ "หาลูกค้าที่ไม่เคยสั่ง" ใช้ตัวนี้ + WHERE OrderID IS NULL
RIGHTSomchai·A1, Somchai·A2, Mana·A3, NULL·A4ฝั่งออเดอร์ครบ
FULLรวมทุกแถวทั้งสองฝั่ง = 5 แถว (Suda และ A4 เป็น NULL คนละจุด)ทั้งสองฝั่งไม่ตกหล่น

6.3 Subquery (ไม่เกี่ยวข้องกัน) vs Correlated Subquery ⭐

Subquery ปกติ (run ครั้งเดียวจบ)

SELECT ชื่อ FROM Customers
WHERE เมือง = 'BKK'
  AND ID IN (SELECT CustID
             FROM Orders);

วงใน "รันตั้งแต่ต้นแล้วจบ" ได้รายชื่อ {1,3} → วงนอกเอาไปเทียบ · เหมือนโน้ตรายชื่อเสร็จแล้วค่อยเอาไปหา

Correlated Subquery (วนรัน "ต่อแถว" ของวงนอก)

SELECT ชื่อ,
 (SELECT SUM(ยอด) FROM Orders o
  WHERE o.CustID = c.ID) AS ยอดรวม
FROM Customers c;

วงในอ้าง c.ID ของวงนอก → ต้องรันใหม่ทุกแถวลูกค้า (Somchai=800, Suda=NULL, Mana=200) · เหมือนเดินไปถามทีละคนว่า "ซื้อไปเท่าไหร่" แล้วจดท้ายชื่อ — ช้ากว่าแต่ทำเคสที่ subquery ปกติทำไม่ได้

แนวคำถาม SQL ที่เคยออก (ฝึกพิมพ์ได้จริง) ① รายชื่อลูกค้าที่ไม่เคยสั่งซื้อ (LEFT JOIN … IS NULL หรือ NOT EXISTS) · ② ยอดรวมสั่งซื้อของแต่ละลูกค้า (correlated subquery หรือ GROUP BY) · ③ ลูกค้าที่ยอดสั่งซื้อสูงกว่า "ค่าเฉลี่ยทั้งหมด" (subquery ใน HAVING) · ④ ออเดอร์ที่ไม่มีลูกค้าตรง (RIGHT/FULL JOIN … IS NULL) · ⑤ ลูกค้าจากเมืองเดียวกับ 'Somchai' (subquery อ้างตารางเดียวกัน)
